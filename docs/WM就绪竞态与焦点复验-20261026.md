# WM 就绪竞态与焦点复验（2026-10-26）

## 定性与历史记录

焦点项是整桌面GUI的必过项，不能因`_NET_ACTIVE_WINDOW`暂不可用而记成环境限制或跳过。Lead补充的0.1.5冷启动14/14，以及同一Computer产物在启动后能正常查询EWMH并切换焦点的证据，支持“会话启动早于WM就绪”的竞态定性。

0.1.4原始独立报告继续保留13/14，不追改历史数字；本轮没有重新创建0.1.4实例，不能把其他版本的复验结果写成0.1.4已经14/14。

## 源码修复

`runtime/desktop-session.mjs`原先只等待`xdpyinfo`成功，随后spawn Fluxbox和终端就返回。X11可连接、Fluxbox进程存在，均不代表WM已经完成窗口接管。

现在冷启动返回会话前，最多轮询5秒：

- `xprop -root _NET_SUPPORTING_WM_CHECK _NET_ACTIVE_WINDOW`须返回WINDOW类型的非零窗口ID。终端开启时两项都必需；无终端的组件测试只要求WM检查窗口。
- `xprop`退出码为0但返回属性不存在、活动窗口为0，均不算就绪；单次命令也有超时和输出上限。
- Fluxbox启动error或异常exit立即作为`DESKTOP_WINDOW_MANAGER_UNAVAILABLE / 503`失败；整体就绪超时同样503。清理半启动的原生桌面后允许重新初始化，不返回虚假的ready。
- 正常镜像仍逐字读取`/etc/X11/fluxbox/keys`，仅ENOENT才回退最小绑定；权限错误继续失败。镜像构建已有可执行文件、绑定文件非空及SHA256校验，本轮没有移除这些约束。

这不是给每次连接固定加5秒延迟：条件满足立即返回。Lead的只读E2E脚本已有最长8秒的WM等待，本方未修改该脚本；产品启动本身的等待上限为5秒。

## 验证结果

```text

true !== false
```

修复后覆盖延迟就绪、非零WM但活动窗口为0的超时/清理/重试、Fluxbox退出和spawn报错。原有完整默认绑定、ENOENT回退、EACCES失败等测试保留。

Node22.23.4全量结果：133项，132通过、0失败、1项需要显式Linux环境的沙箱测试跳过；没有跳过WM或焦点测试。

首次探针用固定终端标题断言失败，原始错误为`condition not ready: node@f8028249bc22: /work`。Shell实际把标题改成了主机名和工作目录；保留失败日志后，仅修正探针，改为匹配XTerm类对应的窗口ID，没有更改产品焦点行为或跳过断言。

此项为本地候选源码覆盖验证，不是不可变新镜像、预发候选源码或Studio页面验收。
