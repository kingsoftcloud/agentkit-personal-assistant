# 桌面本地验证记录（2026-10-25）

本记录覆盖 `ca2c957` 的输入修复和 `3a52441` 的常驻采集实现。验证在 Apple Silicon 本机的 Docker `linux/amd64` 仿真容器中进行，桌面为真实 Xvfb、fluxbox 和 xterm；**不是预发 Pod、AppArmor、网关或 Studio 页面验收**。

原始 JSON、脚本、前后截图、包版本和校验和保存在工作区 `.artifacts/desktop-local-20261025/`。画面文件只作为这次本地测试证据保留，不加入插件包；运行时代码使用 ffmpeg stdout 和内存 Buffer，不保存画面。

## 帧率与 CPU

| 指标 | 原 ImageMagick 每帧启动进程 | 新常驻 ffmpeg |
| --- | --- | --- |
| 实测输出 | 30 帧 / 3655 ms，即 8.21 fps | 61 帧 / 5074 ms，即 12.02 fps |
| 容器 CPU | 120.85% | 38.91% |
| 首帧 | 此基线未统计 | 930 ms，6430 字节 |
| 本次最大帧 | 48941 字节 | 14175 字节 |
| 无输入 10 秒后 | 此基线未统计 | 0.997 fps |

CPU 由容器 cgroup 的 `usage_usec` 差值除以实测时间计算，100% 表示一个 CPU 核。旧方案再叠加每次抓帧后的 100 ms 等待，估算只能达到约 4.51 fps；这项是按实测抓帧耗时计算的估算值。

新采集器固定以 15 fps 生成 MJPEG，使用 `yuvj420p`、两个编码线程，内存中只保留最新完整帧。超过 307200 字节的帧会丢弃；流解析器也限制未完成帧的缓存。活动时提供 80 ms 传输节奏，无输入 10 秒后限制每秒一个新帧。**空闲降帧目前作用于发送频率，采集器仍以 15 fps 工作**；本次空闲容器 CPU 为 32.55%。

依据：`import-baseline.json`、`stream-evidence.json`。本地帧率结果不能证明预发资源配额或网络条件下也满足要求。

## 输入与窗口

在新采集器运行期间，终端实测通过：

- 中文、英文、emoji 输入后，shell 读取的 UTF-8 字节与 `你好，云电脑 English 😀` 完全一致；本次输入到脚本读取回显共 885 ms，包含脚本等待及 Enter 操作，不是网关端到端点击延迟。
- Ctrl+C 中断 `sleep`，后续命令可执行；Tab 完成 Bash 文件名补全；Esc 被终端读为 `0x1b`。
- 输入 `ls` 后，前后 JPEG 不同，原图为 `stream-ls-before.jpg`、`stream-ls-after.jpg`；中文回显原图为 `stream-utf8-after.jpg`。
- xclip 在粘贴请求完成后回收；不使用 `--clearmodifiers`。按键采用独立的按下、抬起事件，关闭控制会话时释放残留按键和鼠标按钮。
- 最小 fluxbox 配置消除了默认壁纸错误窗口；xterm 使用有边框的普通窗口，给浏览器保留独立窗口空间。多窗口浏览器仍需随最终镜像在预发验证。

依据：`input-stream-evidence.json`。本次输入测试不包含 Studio 浏览器的 IME 事件组合、网络延迟和坐标换算。

## 生命周期

同一已打开桌面下连续打开、关闭另外十个观察会话，每轮进程检查均为一套 Xvfb、一套 fluxbox、一个 ffmpeg，`xmessage=0`。最后一个观察会话关闭后，采集进程为零；调用 `dispose()` 后目标 display 的全部进程为零。显示进程在最后会话关闭后可保留至默认 60 秒空闲回收，以供再次打开时复用。

本次没有执行 Pod 删除；该项不能由本地进程清理测试替代。
