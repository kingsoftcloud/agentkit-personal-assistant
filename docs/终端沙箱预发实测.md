# 终端沙箱预发实测（2026-10-25）

当前只证明受限 Bash、Python、Node 执行和列出的拒绝行为可用，**终端能力尚未完整验收**。ABI 1 的安全补偿会阻止工作区内的 `chmod` 和 `ftruncate`，真实 `git init` 因此失败。不能据此宣布 Git、SSH 或所有终端命令可用。

本次在已有真实 Pod 中向 `/tmp` 放入固定来源的 Landlock 启动器、本项目 guard 和测试源码。没有修改 Pod 的权限、AppArmor、容器安全上下文或镜像。新镜像构建、发布和经 Computer HTTP API 的复测仍须另行完成。

## 原始错误与选择依据

```text
bwrap: Failed to make / slave: Permission denied
exit 1
```

相同容器中，原有 `unshare --user --map-root-user --net --pid --fork --ipc --uts --kill-child` 成功。Landlock syscall 返回 ABI 1，固定启动器 `--probe` 返回成功，并提示部分约束需要较新 ABI。

单独使用 Landlock 的反例：对工作区以外自建的 `/tmp/pa-landlock-deny-sentinel` 执行 `os.truncate(path, 0)` 成功，文件变为 0 字节。因此不能把单独的 Landlock 当作可用降级路径。

实际采用的执行顺序：

```text
unshare（user/pid/net/ipc/uts）
  → terminal-guard（libseccomp）
  → 固定 DSH landlock-run（文件允许列表）
  → bash / Python / Node
```

文件读取仅开放 `/usr`、`/etc`、`/dev/urandom`；写入仅开放该执行器的工作区与 `/dev/null`。没有开放 `/proc`，没有共享 `/tmp`，执行环境也不继承 Host token。guard 拒绝截断、文件元数据更改、进程/命名空间特殊接口及 socket。任何一层启动失败，执行器拒绝执行。

离线 linux/amd64 仿真构建只导出 libseccomp 策略；它不能提供实际 enforcement 证据。真实加载使用目标内核的自动探测结果，要求 libseccomp API ≥3，架构不匹配与 x32 调用终止整个进程。此前把离线策略的 API 版本强制用于真实加载曾得到 `seccomp_load=-14 (Bad address)`；现已只在离线导出时固定 API，真实内核探测到 API 6 后加载成功。

## 真实结果

| 检查 | 结果 |
| --- | --- |
| 工作区 `open(..., 'w')`、写入、读取中文 | 成功，内容完全一致 |
| Bash + Python | exit 0，`BASH_OK5` |
| Node JavaScript | exit 0，`7` |
| 工作区外文件读取、写入 | EACCES / 13 |
| 工作区外 `truncate`、`chmod`、`utime` | EPERM / 1 |
| `/proc/<Host pid>/environ` | EACCES / 13 |
| TCP socket、Unix socket | EPERM / 1 |
| `ftruncate` | EPERM / 1，工作区文件内容未变 |
| x32 getpid syscall | SIGSYS，子进程返回 -31 |
| 原生 getpid syscall | 成功 |
