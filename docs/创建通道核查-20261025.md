## 已确认的代码缺陷

1. runtime-service 原先只记录错误类型 `%T`。本地提交 `f5229c4` 增加原始错误与阶段，保留错误链；确定性的 BuildJob 配置错误返回 400，瞬时错误仍保留 503。
2. Server 原先遇到约定的“同一 operation 重试”503 时只请求一次。本地提交 `15ff005f` 对三种明确的重试协议做最多三次有界重试，冻结请求体、身份、operation、摘要、请求头与 request ID；其他 400/409/503 不盲目重试，取消立即停止。
3. Server 的创建 service 捕获同步错误、将记录写成 FAILED 后仍返回带 agent_id 的字典；action 只检查 agent_id，导致 Code 0。正在修复该返回边界，不能将尚未部署的修复算作线上行为。

指定记录已满足这个确定的失败条件：PA 创建请求缺少模型 endpoint，Server 自动补 key 却不补 `OPENAI_BASE_URL`；runtime-service 的 BuildJob 必然拒绝缺少 endpoint 或 key 的上下文，原文为 `personal-assistant requires an authorized model endpoint and API key`。此前该配置错误被泛化成 503。该结论来自指定记录的实际配置与执行分支，不是把 503 推断成镜像或集群故障。

Go `controller/agentctl` 与 `api/service/agents` 整包测试通过；Server 同 operation 重试的 19 项测试通过。runtime-service `f6df59c` 已构建并灰度至 dev API / watcher，镜像摘要 `sha256:15590932fa7e8a906ceb696dc221e738b1c516b2122a4b39a3aa89d06cafb41c`；两者滚动成功。Server 的重试修复当时尚未灰度。

后续正式 UpdateAgent 复验曾出现 `DSH update requires its complete managedRuntimeConfiguration and private host context`（RequestId `b6e0e846-a472-48c1-886b-ff6f8d9f5ef5`），原因是 PA 普通请求与显式 DSH 私有上下文路径不一致。提交 `10ebd5a` 在更新前严格恢复已有密封 Secret/身份绑定，拒绝引用被替换或 manifest 不一致的请求；没有生成替代密钥。测试通过后镜像 `sha256:1869e395a03848a9091ce90bc713023f241fc3c7823dcec586f5af99c65a0514` 已灰度至 dev API/watcher。相同 UpdateAgent 请求复验 Code 0，RequestId `req-20261025230021-bqsojk`；云盘一次挂载超时后正常恢复，新 Pod `36c982a7-5dab-4fed-8a82-393ab9afc571` 已 Ready，CR Running 1/1。
