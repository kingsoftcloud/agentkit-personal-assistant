# 预发验收记录（2026-10-25）

当前已通过真实 Server API 创建个人助理 Agent，AgentRuntime 与 Pod 已出现。现有部署为 0.1.1 基线镜像；本地开发的 DSH Host 与完整桌面尚未部署到此实例。因此，本记录不是完整桌面验收通过报告。

## 创建与 Pod

创建请求使用 `CreateAgentProduct`，运行时选择 `personal-assistant` 的 `0.1.1`，返回 HTTP 200、`Code=0`：

```text
RequestId=req-20261025205816-jzmgnk
AgentId=ar-20261025205816-14494b19
InstanceId=14494b19-8a54-43be-bbbb-a17e9f3b228d
```

可复核命令：

```sh
export KUBECONFIG="$HOME/.kube/config-b56be622-ca25-463a-ba21-55f9070c83ca"
ns=ar-20261025205816-14494b19
kubectl -n "$ns" get agentruntime "$ns"
kubectl -n "$ns" get pod "$ns-0" \
  -o jsonpath='{range .status.containerStatuses[*]}{.name}{" ready="}{.ready}{" restarts="}{.restartCount}{"\n"}{end}'
```

实测关键输出：

```text
phase=Running
agent-runtime ready=true restarts=0
filebeat ready=true restarts=0
personal-assistant-computer ready=true restarts=0
```

这里实际有三个容器，包含平台注入的 filebeat。尚未满足「恰好两个容器」的验收条件。

## Broker 基线

实测 runtime 的 `COMPUTER_BROKER_URL=http://127.0.0.1:8787`，与 computer 端口 8787 一致。computer 的 `/health` 和 `/v1/status` 均返回 200。

第一个 Bot 的租约申请为 200；第二个 Bot 同时申请返回 409、`COMPUTER_LEASE_CONFLICT`。第一个释放后，第二个可以申请成功。

通过 Assistant → Computer Broker 打开 `https://example.com/`，返回标题 `Example Domain`，浏览器截图为 1280×800、67241 字节。该镜像使用 headless Chromium，这只能证明浏览器工具链路，不能算完整 Linux 桌面。

终端执行仍失败，原始错误为：

```json
{"error":"ASSISTANT_CLOUD_EXEC_REFUSED"}
```

Pod 中观测到的 AppArmor 为 `cri-containerd.apparmor.d (enforce)`。集群没有启用 DSH sandbox 的对应配置和节点标签，不能将这个默认 profile 算作 DSH deny profile 验证通过。

## 原验收脚本结果

未修改交接的验收脚本，直接运行：

```sh
KUBECONFIG="$HOME/.kube/config-b56be622-ca25-463a-ba21-55f9070c83ca" \
  bash .scratch/personal-assistant-cloud-computer/e2e-verify.sh \
  ar-20261025205816-14494b19 ar-20261025205816-14494b19
```

退出码为 2。脚本能找到 AgentRuntime，但用 `agentruntime=<name>` 选择 Pod；实际标签是 `agentplatform.k8s.io/agent-runtime=<name>`，因此报告容器数 0、Ready 数 0。上面的直接 Pod 查询证明当前三个容器均 Ready；这不消除「恰好两个」条件本身未满足的问题。
