## Gate 1：确认每个组件的正式发布来源

以下两条路径二选一，当前均尚未作为正式发布来源确认：

1. 将 PA 所需变更整合到该仓库正式默认分支；刷新远端，验证发布提交包含所需变更，并通过对应 CI 和预发回归。
2. 明确指定经过评审的 PA 专用发布分支或标签，记录远端 ref、不可变 commit/tree、该版本的维护与回滚来源；CI 必须从该固定提交构建，不能随后退回 master 重建同名候选。

现有 `codex/personal-assistant-*` 分支是可追溯的预发候选输入，不自动获得正式发布资格。检查覆盖 Runtime Service、Operator、Server、Gateway、Studio、独立插件及 Images；不可只合 Runtime Service 而遗漏配套协议或部署逻辑。

每个发布组件还须核对：

- 发布源码与镜像 provenance 中的 commit/tree 相同，镜像内二进制/产物摘要匹配；完整编译输入来自固定 Git archive。
- Runtime Service 的 Operator/xlog 依赖锁继续通过；默认分支整合后也不能丢弃依赖来源校验。
- registry digest、catalog 同版本记录、实际 Pod imageID 三者一致；新版本追加，不覆盖已验收版本或他人的候选。
- 以正式来源重新构建后的完整链路通过；不能直接沿用旧分支构建的成功报告来证明 master 构建成功。

复核命令（在各仓库中执行；退出码 0 才表示包含）：

```bash
git fetch origin master
git rev-parse refs/remotes/origin/master
git merge-base --is-ancestor <所需候选提交> refs/remotes/origin/master
git rev-list --left-right --count refs/remotes/origin/master...<候选提交>
```

若采用经过确认的 PA 发布分支，将上例的目标 ref 换成相应远端发布 ref，并固定记录其 SHA；单独写一个可移动分支名不算完成。

## Gate 2：目标部署的安全与生命周期

- 在每个目标节点/节点池确认固定 AppArmor 策略已加载为 enforce，主容器与 Computer 均绑定目标策略；containerd 默认 profile 不算通过。
- 确认可信 Operator namespace 白名单、节点摘要标记、最小权限及实际命令/桌面/Host socket 验收；不把 CRD schema、Pod Running 或节点标签当成内核证明。
- Pod Security Admission 与 AppArmor 分别记录。namespace 没有 pod-security 标签不能写成已经启用 PSA；单节点、单 namespace 灰度不能写成全环境沙箱通过。
- 创建、两容器 Ready、真实 GUI/Terminal、Bot 隔离与 lease、空闲释放/恢复、重启数据保留分别出证据。

0.1.11 已有目标 AppArmor 定向灰度证据，但完整 DSH 沙箱门禁仍保持 open。详见[0.1.11 预发报告](./0.1.11-startup-v2与目标AppArmor预发验收-20261026.md)。

## 启动协议 v1 与模板 v2 的区别

当前使用的线协议始终是 `agentengine.dsh-startup/v1`，manifest 传输协议仍为 `runtime-manifest/v1`。`agentkit.personal-assistant.startup/v2` 是 PA 的模板版本，不存在本轮必须等待的 `agentengine.dsh-startup/v2`。

0.1.11 的 catalog 同版本记录已经显式声明：

```yaml
startup:
  protocol: agentengine.dsh-startup/v1
  templateVersion: agentkit.personal-assistant.startup/v2
  command: [/usr/local/bin/agentkit-runtime]
  port: 8080
  healthCheck:
    protocol: HTTP
    path: /ready
```

该模板在真实实例 `ar-20261026071544-e9b4f704` 生成同镜像只读 manifest checker、启动摘要和 HTTP readiness，已验证 checker exit=0。它是现有 v1 协议上的已实现模板，不能因为旧二进制 strings 仅看到 `dsh-startup/v1` 就判定模板不可用；反过来 strings 中有协议名也不能代替实际 CR/Pod 校验。

冻结的 0.1.6 不补写新 descriptor、不重建同名镜像。没有显式 startup 声明的旧 CR 不带启动模板注解，需要与协议支持范围分开判断。
